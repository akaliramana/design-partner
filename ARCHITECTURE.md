# Architecture

Current-state architecture for the design-partner skill suite.

## Suite structure

Three capability groups, one orchestrator:

```
┌──────────────────────────────────────────────────────┐
│                 ui-skill (orchestrator)               │
│                                                      │
│  Detect → Understand → Reason → Design System →      │
│  Build → Integrate → Verify                          │
│                                                      │
│  14 reference files loaded on-demand                 │
│  2 enforcement hooks (PreToolUse + PostToolUse)      │
│  BM25 search engine over curated CSV databases       │
└──────────────────┬───────────────────────────────────┘
                   │
     ┌─────────────┼──────────────┐
     ▼             ▼              ▼
  Core UI/UX    Prototype      Branding
  ui-styling    prototype      brand
  design-system                design
                               slides
                               banner-design
```

**Most users only interact with `ui-skill`.** It routes to sub-skills as needed.

## Source of truth model

The skill operates in two modes based on what the project already has:

| Project state | Design system source of truth |
|---|---|
| **Has existing tokens/theme/components** | Adopted from project files. MASTER.md is an adoption record. |
| **No existing design system** | Generated by search engine. MASTER.md is the generated system. |

Detection runs automatically in Phase 0. The skill looks for: `DESIGN_SYSTEM.md`, `theme.js/ts`, custom Tailwind theme, CSS custom properties, and component patterns.

## Pipeline

Each phase produces an artifact the next phase requires:

| Phase | Produces | Gate |
|---|---|---|
| **0: Detect** | Project state + design system detection | Must classify project before proceeding |
| **1: Understand** | Product context (user, goal, primary action) | Must know context before reasoning |
| **2: Reason** | Layout options with trade-offs, user selection | Must have user's choice before building |
| **3: Design system** | Adopted or generated tokens in MASTER.md | Must exist before any code is written |
| **4: Build** | App files, components, pages, state files | Must complete ALL sub-steps atomically |
| **5: Verify** | Lint, build, route checks, visual review | Must pass before declaring done |

**Key enforcement:** Planning is not a deliverable. Phases 3→4→5 execute as a continuous pipeline after the user selects a layout. Stopping after Phase 3 is treated as failure.

## State files

Per-project state stored in `.ui-skill/`:

| File | Purpose |
|---|---|
| `registry.json` | Shared component tracking — file paths, which pages use each component, props |
| `manifest.json` | Page/screen tracking — routes or screen IDs, navigation items, page relationships (parent/child, linksTo) |

The manifest supports two host app models:
- **`route-path`** — Pages are route files, keys are URL paths (`/`, `/settings`). Default.
- **`screen-id`** — Single-shell apps, keys are screen names (`dashboard`, `settings`).

## Design system adoption

When an existing design system is detected, the skill:

1. **Audits** — reads all design system files, assesses completeness (colors, typography, spacing, components, responsive rules)
2. **Reports** — tells the user what it found and what it will adopt
3. **Adopts** — uses existing tokens as source of truth, does not overwrite
4. **Fills gaps** — only invents patterns for what's missing
5. **Records** — writes MASTER.md as an adoption record with source file references

See `references/design-system-audit.md` for the full audit protocol.

## Product integration

For existing projects, building a screen means integrating it into the product:

1. **IA placement** — determine if the screen is global nav, role-specific, sub-page, or deep-link-only
2. **Navigation integration** — add to the existing nav component, never create parallel navigation
3. **Desktop + mobile parity** — every nav-reachable page must be reachable from both surfaces
4. **Shell consistency** — use the same layout wrapper as other pages at the same level
5. **Production states** — empty, loading, error states matching existing patterns (for production apps)
6. **Shared component impact** — verify changes don't break other pages

See `references/product-integration.md` for the full integration protocol.

## Stack support

The reasoning, design system, and prototype layers are stack-agnostic. Stack-specific behavior only applies at the build layer:

| Concept | Next.js | React + Vite | HTML + Tailwind |
|---|---|---|---|
| CSS entry | `src/app/globals.css` | `src/index.css` | `styles/globals.css` |
| Root layout | `src/app/layout.tsx` | `src/App.tsx` | `index.html` |
| Font loading | `next/font` | CSS `@import` | `<link>` tag |
| Routing | File-based (App Router) | React Router | `<a href>` |

See `references/stack-paths.md` for the full mapping.

## Enforcement

| Mechanism | How it works |
|---|---|
| **PreToolUse hook** | Warns if writing to `src/` without `design-system/MASTER.md` existing |
| **PostToolUse hook** | Warns if a `.tsx`/`.jsx` component lacks responsive Tailwind classes |
| **Phase checklists** | Each phase has a checklist that must pass before proceeding |
| **Completion gate** | Multiple conditions must all be true before the skill reports "done" |
| **Artifact gates** | Each phase's output is required by the next phase — skipping is structurally difficult |

## Installer

`install.sh` copies the skill suite into a project:

1. Copies `.claude/skills/` (all skill modules)
2. Patches ESLint config to ignore `.claude/**` (handles flat config, legacy JSON, and `.eslintignore` — uses `scripts/patch-eslint.js` for reliability)
3. Creates `.ui-skill/` with empty state files
4. Creates `CLAUDE.md` with build pipeline instructions
5. Creates `design-system/` directory
6. Verifies Python 3 and skill files exist

The installer is idempotent — safe to run twice.

## Sub-skill integration

Three sub-skills have integration headers that reinforce the orchestrator's rules:

- **ui-styling** — Read design tokens from source of truth, register components, responsive required
- **design-system** — MASTER.md is source of truth, include reasoning for every token choice
- **brand** — Read tokens from source of truth, build only what's asked for, ask format preference

Other sub-skills (design, slides, banner-design) operate independently as companion workflows.

## Knowledge base

The BM25 search engine (`scripts/search.py`) searches curated CSV databases covering:
- Product types and UI patterns
- UI styles with CSS keywords and implementation checklists
- Color palettes by industry/product type
- Typography pairings with Google Fonts imports
- UX guidelines and anti-patterns
- Chart types and data visualization
- Stack-specific guidelines (React, Next.js, Vue, Svelte, etc.)
- Landing page structures and CTA strategies

The search engine supports domain-specific queries (`--domain style|color|typography|ux|...`) and design system generation (`--design-system --persist`).
